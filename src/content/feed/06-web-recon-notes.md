信息收集最容易变成"工具轮流跑一遍"，跑完一堆文件，真要用的时候什么也找不到。这篇记的是我目前的一套流程：先把目标拆成资产，再按层收集，最后整理成能直接拿去用的东西。

**所有操作都在授权范围内进行。** 没拿到书面授权的目标，只做公开信息查询，不做主动扫描。

## 先建资产模型

拿到一个域名，别急着扫。先回答四个问题：

1. 它有哪些子域、哪些 IP；
2. 这些 IP 开了哪些端口、跑什么服务；
3. 服务上是什么应用、什么版本；
4. 哪些是真正的入口，哪些只是 CDN 或负载均衡。

对应的是一条链：**域名 → IP → 端口 → 服务 → 应用**。每一层都可能漏，也每一层都要落表。

## 被动收集：不碰目标也能拿到很多

先从公开信息开始，这一步对目标零打扰。

```bash
whois example.com
dig +short A example.com
dig +short NS example.com
dig +short TXT example.com
```

TXT 记录经常能翻出 SPF、验证串、甚至内部系统名。NS 记录能看出用的是哪家 DNS，云厂商的 NS 往往意味着后面还有一批同厂资产。

子域枚举优先用证书透明度日志，因为证书是公开的：

```bash
curl -s 'https://crt.sh/?q=%25.example.com&output=json' \
  | jq -r '.[].name_value' | sort -u
```

再用 subfinder 补被动源：

```bash
subfinder -d example.com -all -silent | sort -u > subs.txt
```

别忘了 GitHub。很多泄露的密钥、内网地址、测试域名，都是有人顺手提交到公开仓库的。搜 `"example.com" password`、`"example.com" api_key` 这类组合，比扫端口有用得多。

## 主动收集：先确认边界，再动手

被动结果去重、解析：

```bash
dnsx -l subs.txt -a -resp -silent
```

端口和服务识别：

```bash
nmap -sV -Pn -p- --min-rate 1000 -oA nmap/full 1.2.3.4
```

全端口扫很吵，先确认授权允许，必要时降速、分时段。只扫常见端口是新手最容易犯的错——真正的后台经常在 8080、8443、9000 这种地方。

Web 指纹和标题批量看：

```bash
httpx -l alive.txt -title -tech-detect -status-code -silent
```

目录爆破要克制：

```bash
ffuf -u https://target/FUZZ -w wordlist.txt -mc 200,301,302,403 -rate 50
```

还有一个经常被忽略的来源：**前端 JS**。把页面引用的 js 下载下来，grep 接口路径、AK/SK、内网地址，往往比目录爆破更快命中。

## 整理：收集的终点是表，不是文件夹

我现在固定输出三样东西：

- `assets.csv`：域名、IP、端口、服务、指纹、状态；
- `evidence/`：每个结论对应的截图或响应片段；
- `notes.md`：时间线、可疑点、下一步。

去重和排序比多跑一个工具重要。同一个应用在 CDN 后面有十个 IP，真正需要测的只有一个域名——不整理就会把时间浪费在重复目标上。

## 几个坑

**只看 80/443。** 非标端口才是后台和高危服务的聚集地。

**把 CDN 当源站。** 解析到 Cloudflare 就去打，打的都是别人的边缘节点。要看历史解析、证书、源站泄露。

**不限速。** 全速跑目录爆破，轻则被封 IP，重则触发对方告警，授权测试也会被叫停。

**WAF 误判。** 403 不一定代表"没东西"，可能是 WAF 在拦；换个 UA、降速、看响应体差异，别急着下结论。

**不做记录。** 打完就忘，复现不了，报告写不出来。证据要边打边留。

## 从防守方看这件事

站在甲方视角，信息收集对应的是三件事：

1. **资产台账**：自己都不知道有哪个子域、哪个 8080 端口，就别谈防护；
2. **攻击面收敛**：测试环境、旧系统、默认页面，能下线就下线；
3. **暴露面监控**：证书透明度、公开仓库、DNS 变化，都该有告警。

攻击者看到的东西，防守方应该先看到。信息收集这门课，学的其实是怎么把自己的影子找全。
